# Video Download Helper テストガイドライン

このドキュメントは、Video Download Helper におけるテストの書き方・運用方法をまとめたガイドラインです。基本ルールは `CLAUDE.md` および `品質チェック・テスト規約.md` にも記載しています。

本拡張のテスト戦略は **「コアロジック層の純粋性」** に全面的に依存しています。HLS / DASH の解析、URL 正規化、重複排除、ファイル名生成といった実質的なロジックを `chrome.*` から切り離しておくことで、その大半を高速な Unit テストで検証できます。この分離が崩れた時点で、テストは Chrome 起動を伴う遅く不安定なものへ退化します。

## テストの種類と構成

| 種類 | 配置場所 | 実行環境 | 実行コマンド | 用途 | 状態 |
|------|----------|----------|-------------|------|------|
| ユニットテスト | `src/**/*.test.ts` | Vitest (node) | `pnpm test:unit` | コアロジック層（`shared/` `media/` `processor/`）の検証 | Phase 1 で導入 |
| コンポーネントテスト | `src/popup/**/*.test.tsx` | Vitest (jsdom) + Testing Library | `pnpm test:unit` | Popup の描画・キーボード操作の検証 | Phase 1 で導入 |
| 統合テスト | `test/integration/` | Vitest + Chrome（拡張機能ロード） | `pnpm test:integration` | `chrome.*` に依存する層（storage / messaging / webRequest）の検証 | Phase 1 で導入 |
| E2Eテスト | `test/e2e/` | Playwright | `pnpm test:e2e` | 検出からダウンロード完了までのユーザーフロー検証 | Phase 1 で導入 |

## CI実行フロー

PR が作成されると、以下が実行されます。

```text
PR Created / Push to main
  ├── verify.yml
  │   ├── pnpm lint          （Biome: フォーマット + lint）
  │   ├── pnpm typecheck     （tsc --noEmit）
  │   ├── pnpm test:unit     （Vitest ユニット + コンポーネント）
  │   ├── pnpm depcruise     （依存方向チェック）
  │   └── pnpm build         （Vite + CRXJS ビルド検証）
  └── ci.yml
      ├── pnpm test:integration  （Chrome 起動）
      └── pnpm test:e2e          （Playwright）
```

全ステップがパスするとマージ可能になります。

## ユニットテスト

### 対象

- 外部依存のない純粋関数（`shared/` `media/` `processor/`）
- HLS Master Playlist / Media Playlist 解析
- DASH MPD 解析（AdaptationSet / Representation / SegmentTemplate / SegmentList / BaseURL）
- URL 正規化・相対 URL 解決
- Content-Type / 拡張子からの形式判定
- 重複メディア排除（ネットワーク検出と DOM 検出の統合）
- ファイル名生成
- DRM 候補判定
- ブロックリスト対象サイト判定
- TS / fMP4 セグメント形式判定
- Popup の表示用整形関数（バイト数、解像度ラベル、ビットレート表記）

### 配置ルール

実装ファイルと同じディレクトリに `*.test.ts` として配置します。

```text
apps/extension/src/
├── media/
│   ├── hls/
│   │   ├── parser.ts
│   │   └── parser.test.ts        ← 同階層に配置
│   └── blocklist.ts
│       └── blocklist.test.ts
└── processor/
    ├── filename.ts
    └── filename.test.ts
```

### ポイント

- **mock は極力使わない**: 対象のロジックを純粋関数として切り出してからテストする。`chrome.*` をモックしないと書けないテストは、設計側が間違っているサインとして扱う
- **マニフェストはフィクスチャとして持つ**: パーサーのテストは `test/fixtures/hls/*.m3u8` / `test/fixtures/dash/*.mpd` に実データ由来のサンプルを置き、文字列を受け取る関数として検証する。ネットワークアクセスは行わない
- **Port は Fake で差し替える**: `MediaFetcherPort` / `DownloadPort` 等はインターフェースとして定義し、テストでは Fake 実装を注入する。`vi.mock` によるモジュールモックは使わない
- **異常系を必ず書く**: マニフェストの破損、`#EXT-X-STREAM-INF` の属性欠落、想定外の Content-Type、相対 URL の解決失敗など。パーサーは外部入力を扱う境界であり、正常系だけのテストは意味を持たない

## コンポーネントテスト

### 対象

- Popup の各コンポーネント（`MediaList` / `MediaItem` / `QualitySelector` / `DownloadProgress` / `StatusMessage`）
- 状態ごとの表示（検出中 / 未検出 / 一覧 / ダウンロード中 / 完了 / エラー / DRM）

### 設計方針

- Testing Library を使い、実装詳細ではなくユーザーから見える振る舞い（ロール・ラベル・テキスト）で検証する
- `chrome.runtime` へは Fake port を注入する。Popup 側の hooks が port を引数または Context 経由で受け取れる設計にしておく
- **キーボード操作のみでダウンロードまで到達できることを検証する**（要件定義 2.5 のアクセシビリティ要件）
- 長大なタイトル・URL を渡してレイアウトが破綻しないことを検証する

## 統合テスト

### 対象

- `chrome.storage` を用いる Repository（`shared/storage/`）
- コンテキスト間メッセージング（`shared/messages.ts` の送受信）
- `chrome.webRequest` によるメディア検出パイプライン
- Offscreen Document の生成とセグメント結合

### 前提

- `pnpm build` 済みの `apps/extension/dist/` が存在すること
- テスト用の静的 Web サーバーが起動していること（`test/fixtures/pages/` を配信）

### 設計原則

#### 1. 実際の Chrome で実行する

`chrome.*` API のモックを自作しない。Playwright の `launchPersistentContext` で拡張機能をロードした実 Chrome に対してテストする。モックした `chrome.storage` は本物の制約（構造化クローン、容量上限、`session` の生存期間）を再現せず、テストが通っても実環境で壊れる。

#### 2. 外部ネットワークへ出ない

テスト対象のメディアはすべてローカルの静的サーバーから配信する。以下のフィクスチャページを用意する（要件定義 11.2）。

```text
HTML5 MP4
HTML5 WebM
HLS 1080p / 720p / 480p（TSセグメント）
HLS fMP4セグメント（#EXT-X-MAP）
DASH Video + Audio
Audio Only
SPAで後からvideo要素追加
SPA内遷移での検出結果維持・通常遷移でのリセット
XHRからm3u8取得
blob URL再生
```

#### 3. storage の状態を必ず検証する（最重要）

**メッセージの戻り値だけでなく、`chrome.storage` の状態を必ず検証する。** Service Worker が停止しても復元できることを保証するための検証であり、ここを省くと非常駐前提のバグを一切検出できない。

```typescript
// 良い例: storage の状態も検証
await sendToBackground({ kind: 'start-download', request })

const tasks = await readSessionStorage('download-task:')
expect(tasks[0].status).toBe('downloading')  // 復元可能な形で保存されたことを確認
```

#### 4. Service Worker 停止を再現する

長時間処理が Offscreen Document 側で継続することを検証するため、ダウンロード中に Service Worker を明示的に停止させ、再起動後に状態が復元されることを確認する。**これは本拡張で最も壊れやすい箇所であり、統合テストの中核。**

#### 5. エラーケースの状態検証

マニフェスト再フェッチが 403 を返す、セグメント取得が途中で失敗する、といったケースで、タスクが `failed` として記録され、中途半端なファイルが `chrome.downloads` へ渡されないことを検証する。

#### 6. クリーンアップを徹底する

テストで作成した `chrome.storage` のエントリとダウンロードファイルは `afterEach` で必ず削除する。ブラウザコンテキストはテストファイル単位で使い捨てる。

## E2Eテスト

### 対象

要件定義 11.3 のクリティカルパス。

1. テストページを開く
2. 動画を再生
3. 拡張機能がメディアを検出
4. バッジに件数が表示される
5. ポップアップを開く
6. 動画情報が表示される
7. 画質を選択
8. ダウンロード実行
9. ファイルが正常に生成される

加えて以下を検証する。

- ブロックリスト対象サイトで機能が無効化されること
- タブごとに検出結果が分離されていること（2 タブで相互汚染しない）
- ポップアップを閉じて再度開いても進捗が復元されること
- **拡張機能起点の外部ホストへのリクエストが 0 件であること**（プライバシー要件の機械的検証）

### 設計方針

- Playwright の `launchPersistentContext` + `--load-extension` + `--headless=new` を使用（拡張機能は従来の headless では動作しない）
- 拡張機能 ID は起動ごとに変わるため、Service Worker の URL から動的に取得してポップアップ URL を組み立てる
- ダウンロード完了は `chrome.downloads` の状態ではなく、実際に生成されたファイルのサイズと先頭バイト（TS なら `0x47` 同期バイト）で検証する
- CI ではビルド後に実行する

## テスト作成時の注意事項

### テスト追加が必要なケース

以下のケースではテスト追加が必須です：

- **HLS / DASH パーサーの変更**（対応サイトの増減に直結するため）
- **URL 正規化・重複排除ロジックの変更**（一覧の見え方が壊れるため）
- **ブロックリスト判定・DRM 判定の変更**（ポリシー違反に直結するため）
- **Service Worker の状態復元に関わる変更**

加えて、以下のケースでもテスト追加を推奨します：

- 新しいユーティリティ関数の追加
- 既存ロジックのリファクタリング（回帰テストとして）
- バグ修正（再発防止テストとして）。特定サイトで検出できなかった場合は、そのマニフェストを匿名化してフィクスチャに加える

### describe/it の構造化

関連するケースは `describe` でグループ化し、意図を明確にします。パーサーのテストは「正常系 / 属性欠落 / 不正な形式 / 相対 URL」のように入力の性質で分けます。

### フィクスチャの匿名化

実サイトから採取したマニフェストをフィクスチャに加える際は、ホスト名・認証トークン・セッション ID を必ずダミー値へ置換します。テストデータに実際の認証情報を含めてはいけません。

### 一意性の確保

ダウンロードファイル名やタスク ID には実行ごとに一意な値を含めて、並列実行時の衝突を防止します。

### PR 前の確認

```bash
# 開発中に手元で実行・確認
pnpm test:unit --watch

# PR 作成前に一式を実行
pnpm verify
pnpm test:integration
pnpm test:e2e
```
